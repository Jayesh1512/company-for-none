### Implemented API and exact wiring

Exports: `createAgentProofs`, `AGENT_PROOF_SDK`, `DSTACK_VERIFIER_IMAGE`. Factory accepts frozen private ports `{journal,trust,verifyTeeQuote?,observeFinality?,getTrustedCheckpoint?,sdk?,clock?,limits?}`. Methods `capture({expected,proof,statusEvidence,teeEvidence})` and `replay({evidenceRef,expected})` return `{status:'verified'|'pending'|'unavailable'|'invalid',code,stages:{audit,binding,tee,finality},evidenceRef,...}`. Every result explicitly grants neither spending nor delivery authority. No wallet, signing, transfer or financial mutation exists here. The `sdk` port is trusted server/test composition only, never request JSON; normal execution imports the pinned official package.

`expected = {agentId,accountId,correlationId,action:'transfer',payload:<exact normalized admitted provider body>,requestFingerprint:fingerprint(payload),requiredEvent:'execute.completed'}`. The payload fingerprint is **not** the fingerprint of the full local Rules action. For the existing transfer adapter derive immutable `{confidential:true,asset:action.money.asset,amount:action.money.amount,recipient:action.recipient}` and hash that body.

Account, execution type and request must be in cryptographically committed terminal fields/evidence. Missing committed account/type/request is `unavailable`; mismatches/tampering are `invalid`. The SDK's flexible audit fields do not guarantee those fields exist on a particular deployed event. The captured original provider status must match the requested agent/correlation/type, but its SUCCESS alone never establishes verification.

`trust` requires independently pinned `{origin,witnessPublicKey,apiBaseUrl,expectedAppId,allowedComposeHashes,allowedOsImageHashes,kmsRoot,dstackVerifierImage,network}`. Optional `getTrustedCheckpoint({trust,expected,signal})` returns an actually witnessed or privately retained SDK Checkpoint. It can select the exact independent head used for that operation's `from_size` proof. It must never take a head from the raw proof/request. Otherwise the module uses official fresh witness acquisition. Retrieval/proof alignment is the adapter's read-only acquisition responsibility; missing required acquisition remains unresolved.

`verifyTeeQuote({attestation,quoteHash,expectedReportData,trust,teeEvidence,signal})` must call the actual controlled, pinned dstack quote verifier, returning `{source:'dstack-verifier',verifierImage:DSTACK_VERIFIER_IMAGE,quoteHash,verdict:<raw verifier JSON>}`. `quoteHash` is SHA256 of the exact opaque attestation string in UTF-8. `teeEvidence.info` is the actual matching `/tee/info` record; module verifies its compose hash and KMS settings against the quote and policy. Caller-supplied/provider `valid:true` or `verified:true` is not a port or sufficient evidence. A missing actual verifier is `unavailable` even if all SDK audit checks pass. The module does not launch a verifier service.

`observeFinality({expected,transactionHashes,network,committedEvidence,statusEvidence,signal})` must independently read named NEAR transactions and return `{source:'near-rpc',network,transactions:[{hash,response:<actual RPC response>}]}`. Module requires matching hash, `final_execution_status:'FINAL'`, overall SuccessValue and no observed receipt Failure. It verifies finality of the audit-linked transactions; it does not invent a confidential balance proof or independently reconstruct cross-chain swaps/fees. Non-NEAR settlement routes have no implemented verifier here.

Capture defaults: 2 MiB total private artifact, 256 events and 10-second port timeout; capture storage failure returns unavailable. Artifacts/expected IDs/trust fingerprint/retained checkpoints are private, content hashes checked again on replay, no public ledger events. Replay reruns real SDK crypto and actual quote/finality ports; captured past verdicts or passed booleans are never trusted. An old valid execution is not required to acquire a fabricated new event timestamp; current M01 readiness/authorization preflight remains separate before effects.

### Limits that must stay visible

An Agent API confidential transfer's intent hash is documented provider settlement evidence with no separate public on-chain transaction to verify. Thus **SUCCESS plus intent hash remains unavailable/unknown** in this strict module even with a valid audit proof. It must not be promoted to independently proven funds movement. Public receipts can compare exact payment terms but intentionally omit payer account/grant/request identity, so they do not replace this identity-bound audit step; no receipt-only shortcut was added. Native-chain finality, actual fees, owner-policy/grant verification and any future confidential verification route remain separate evidence work. [Official receipts guide](https://docs.agentsonintents.com/integration/agent-api/receipts), [official status/finality guide](https://docs.agentsonintents.com/integration/agent-api/status-and-errors).

## Journal behavior

Caller chooses the store location; composition currently selects `.runtime/research-shop`. Tests always use disposable OS temp directories. One local application process owns a directory; concurrent in-process handles share one serialization queue. An active writer prevents another process opening the same store; a dead local PID lock is recovered. Foreign/unknown locks fail closed. A crash during the rare stale-lock recovery claim itself can require inspecting that claim; no expired lease is used to steal a live writer.

Each synchronous transaction callback mutates a private clone; atomic temp-write/fsync/rename/directory-fsync commits facts, events, operation registry and command result together. Every committed command stores immutable action fingerprint and result. Replaying returns the stored result before CAS; changed payload identity or stale expected version throws `CONFLICT`. Record CAS is supported through `tx.put(...,{expectedVersion})`. External calls must remain outside transactions. A post-rename error is `COMMIT_UNKNOWN`; replay the same identity to resolve it. Abandoned pre-rename temp files are ignored, never treated as commits. The complete snapshot is rewritten per commit: suitable for this small local MVP, not an unbounded production database.

Operation intent is immutable, observations append to operation history, pending/unknown are recoverable, and confirmed status cannot regress. Artifact content remains in private records; refs include hash/media type/visibility. Files use mode 0600 and newly created store directories 0700. Known raw credential field names are rejected; callers must supply sanitized provider facts and must never put credentials in arbitrary text/artifact content. Journal snapshots are private APIs and must never be rendered publicly.

## Treasury exact plans and snapshot

FinancialSnapshot has schemaVersion/version, controlled `balances:[Money]`, disjoint funded `protectedFunds:[{id,purpose,orderId?,obligationId?,...Money}]`, `dailyCosts:{day:nanoUsd}`, reservations, credit lots and aggregate available credit, obligations, allocations, approvedPlans, consumedPermits, receipts, refunds and latePayments. `snapshot()` supplies the current UTC day as zero when no actual expense is recorded; uncertain upper bounds remain separate reservations with their original accounting day.

`applyDecision` accepts `decision.status:'allow'`, canonical `plan.kind` (compatibility alias `type`) and exact plans: bootstrap, allocation, late_payment, reservation, funding, consumption, payout authorization, refund_intent, confirmed refund and reconciliation. It returns the journal envelope `{replayed,version,result:{financial,duplicate}}`. Financial version is independent of unrelated journal/provider writes. It checks financial CAS, optional current Rules epoch, same units, conservation and record identity. No price, split, cap, retry, refund eligibility or provider choice is calculated here.

- Bootstrap is exact fixture money/provenance with receipt ID, only on an empty financial store; emitted separately as `fixture.bootstrap`.
- Allocation records revenue and exact obligations once by settlement ID. Treasury + contributorReserve must conserve the revenue; the exact additional funded refundReserve may use actual bootstrap cash. All funded protected cash must fit controlled balances. Contributor reserve IDs are `contributor:<obligationId>`; refund reserve IDs are `refund:<orderId>`. Refund exposure is contingent and separate from protected cash.
- Late payments book incoming cash and matching refund reserve once, emit `payment.late`, and create no sale/contributor obligation. Incoming receipt identity is shared with accepted sale allocation so the same receipt cannot be booked both ways.
- Funding debits exact approved cash and adds an owned/provenance-tagged credit lot. It does not record inference expense. Consumption records exact reconciled charge, remaining credit and reservation status. Unknown reservations persist across restart and UTC rollover.
- Payout plan application freezes instruction only. M09 commits provider result, operation status and M03's confirmed progress/reserve debit in one transaction via `applyPayoutResult`. It does not subsequently apply M01 `payout_record` again. Partial confirmed payments preserve completed progress and can receive a new Rules-approved remaining-payment action; pending/unknown operations cannot be replaced.
- Refund intent freezes an instruction only and checks it has the matching funded refund bucket. Confirmed refund applies exact releaseProtected, cash decrement, obligation statuses and zero exposure supplied by Rules. Paid contributions remain paid_before_refund and are never clawed back. No reserve/allocation reversal occurs on pending or unknown results.

Permit protocol: evaluate at v; applyDecision records approvedPlans inputVersion v/appliedVersion v+1; M01 validateDispatch returns fresh decision at v+1; pass it and original permit to consumePermit; exact original plan/fingerprint/version proof is required. Consumption records v+2 and retains the original signed permit, authorizedFinancialVersion and previousFinancialVersion. Re-read facts and call M01 dispatch immediately before the provider. Unrelated financial changes cause conflict and require Rules reevaluation. Never override a stale decision using expectedVersion alone.
