## Private composition and source boundary

```js
createRules({
  // Existing setup/commercial options are unchanged.
  getSupportFacts: action => readSupportFacts({journal, companyId, action})
})
```

Private callback returns company-scoped arrays `services`, `conversations`, `messages`, `tickets`, `agents`, `documents`. For an operation exposing source text, it additionally returns `sourceActionId:action.id` and actual native-read `sources` from the domain's private per-journal/action cache:

```js
{ documentId, title, revision, hash: fingerprint(markdown), markdown }
```

Rules ignores caller `facts.sources`, state, publication flags and proof fields. The only ordinary request facts are `{access,input}`. Snapshots must have exact shape, valid full-markdown fingerprint and the metadata title; each must match the owner-published document ID/revision/hash. No source cache survives a process restart, and a new view/reply requires new actual reads. Native revision changes without local metadata changes are caught by the canonical snapshot check.

Publication requires both `visibility:'company'` and an explicit existing `document.agentIds` grant to the real ready service agent. A general company visibility flag alone cannot authorize this public path. Every reply and customer transcript projection rechecks current publication, grants and canonical snapshots. Old assistant excerpts/citations are replaced by a fixed stale-source notice if any prerequisite is missing; private history remains recorded. Owner inbox access does not imply customer or agent identity.

## Frozen actions and plans

Actions use `{id,type}`. `conversationId` is required only for `support_context`, `support_view`, `support_reply`, `support_escalate`; it is disallowed for the other support actions. Inputs reject unknown fields.

| Action | Input and authority | Exact result |
| --- | --- | --- |
| `support_catalog` | `{}`, public | `plan.services`, only currently metadata-bound owner-published fictional services, no source text/IDs or customer records |
| `support_owner` | `{}`, verified owner | Safe services/conversations/messages/tickets and Rules limits; token hashes excluded |
| `support_publish` | Verified owner; `{serviceId,version,agentId,name,description,kind:'policy'|'claims',fictional:true,sources:[{documentId,revision,hash}]}` | Exact service put with CAS; full current native source snapshots required; event `support.published`; `plan.service` |
| `support_open` | Server input `{serviceId,conversationId,tokenHash}`; new random capability generated by domain | Exact conversation put, event `support.opened`, token-free `plan.conversation` |
| `support_context` | `{}`, verified own customer capability | Fixed published source bindings/agent ID and max source characters for actual private native reads; no public raw knowledge role |
| `support_view` | `{}`, verified own customer capability | Own conversation/transcript/tickets, no token hash; stale/unavailable excerpts redacted |
| `support_reply` | `{text}`, verified own customer capability | Atomic customer+assistant message puts, conversation CAS, optional real ticket; events `support.replied` and optional `support.escalated`; `plan.reply`, `plan.ticket`, `plan.conversation` |
| `support_escalate` | `{summary?}`, verified own customer capability | Exact persistent local ticket + conversation CAS/event; works with stale publication, subject to kill/caps |

All plans have `{kind,puts,events,replyMode:'policy_lookup',aiEnabled:false,fictional:true,providerCalled:false,grantsSpendingAuthority:false}`. Rules itself performs no provider I/O; domain performs actual JBrain reads. No Cloud/model/paid provider is called. Puts are `{namespace,id,value,expectedVersion:null|number}`; null means create/CAS0. Only supportServices/supportConversations/supportMessages/supportTickets are written. Domain reevaluates synchronously at the journal commit boundary.

Service records use the agreed fields `{id,companyId,agentId,name,description,kind,replyMode,aiEnabled,fictional,status:'published',sources,version,createdAt,updatedAt}`. Conversation records store only a token hash; no raw token appears in a Rules projection. Owner requests require the real server-verified owner. Customer access is constructed only by the domain after timing-safe capability verification:

```js
{ role:'support_customer', verified:true, companyId, conversationId, serviceId }
```

The capability must match that exact conversation/service. It is never represented as a fabricated owner or agent. Domain rechecks the token binding at commit. Replaying a message returns a freshly validated/redacted transcript projection, not a stored plaintext answer blindly.

## Reply behavior

Lookup is deterministic model-free retrieval over actual current approved markdown. M01 removes frontmatter, separates heading sections while preserving exact LF/CRLF bytes, scores question terms/section titles, narrows explicit auto/home/travel categories and returns at most3 exact excerpts. Every citation is `{documentId,title,revision,hash,section,excerpt}` and every excerpt is a substring of the published full native source. The response clearly identifies fictional policy lookup, source excerpts and no AI-generated answer or claim/coverage/legal/medical decision.

Unknown specific questions do not match merely because a general policy title contains “auto”. Unknown/no-match, approval/adjudication, personal coverage decisions, reimbursement/payout and legal/medical decision requests create an actual private owner-visible local ticket; they never fabricate an approved claim or external handoff. Selection is a bounded keyword policy, not semantic language-model reasoning. Unmatched wording truthfully escalates.

Reply reasons: `SUPPORT_POLICY_EXCERPTS`, `SUPPORT_NO_MATCH_ESCALATED`, `SUPPORT_CLAIM_DECISION_ESCALATED`. Explicit case reason: `SUPPORT_OWNER_REVIEW_REQUESTED`. Customer message IDs are `${action.id}:customer`, assistant `${action.id}:assistant`, ticket `${action.id}:ticket`.

Stale publication/native source/grant mismatch holds `SUPPORT_PUBLICATION_STALE` with no new messages. The customer may explicitly escalate their own conversation. Missing access denies `ACCESS_DENIED`; conflicting metadata version denies `SUPPORT_VERSION_CONFLICT`; malformed input denies `SUPPORT_INPUT_INVALID`. No caller source or verified boolean can override these holds.

## Limits and existing safety

Rules limits:20 services/company,4 sources/service,24000 characters/source,100 conversations/company,50 customer turns/conversation,20 tickets/conversation,2000 characters/question or escalation summary,3 excerpts of at most1200 characters each,120-character service names,600-character descriptions. Limit codes are `SUPPORT_SERVICE_LIMIT`, `SUPPORT_CONVERSATION_LIMIT`, `SUPPORT_TURN_LIMIT`, `SUPPORT_TICKET_LIMIT`.

Explicit configured kill blocks support publication/open/reply/escalation; customer views redact excerpts and catalog becomes empty. Owner can still inspect their inbox. A missing commercial config in explicit setup mode does not fabricate a kill/grant/model/wallet policy: the narrow zero-paid lookup remains usable. Invalid explicit config remains invalid. Support decisions receive no paid permit or unrelated live authorization metadata.

Existing public research private-knowledge prohibition remains enforced, and setup-only inference/funding/activation/service-order paths remain held. USD5 lifetime ceiling and all original SDK proof/credit/custody rules are untouched. No real claim approval, transfer, wallet, email, insurer API or paid inference path was added.
